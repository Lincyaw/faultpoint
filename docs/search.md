# 因果拼接搜索

`search/` 中的 `faultsearch` 在 faultpoint 的故障点之上做因果拼接：在多个已有的工作负载中各注入一个故障，用反事实故障分析比较注入与对照得到因果边，再把在不同工作负载中观察到的边拼接成跨越多个激活条件的传播链，并在合并的负载中端到端验证。`examples/shop` 是它的第一个被测系统。本文说明这一层的思路、它用到的数据文件，以及在 shop 上的初步结果。

## 1. 思路

级联故障需要多步传播，每一步由自己的条件激活。往往没有哪一个已有的工作负载同时满足所有条件，但每一步都能在某个更宽松的负载中单独触发。因此在许多负载中各注入一个故障，记录注入引起的额外故障，再把这些边拼接起来。

| 概念 | 本层的做法 |
| --- | --- |
| 故障与观测的共同词汇 | 故障是（故障点，动作），观测是（故障点，outcome，指标）；两者通过效果映射（第 3.3 节）对应 |
| 已有的工作负载 | `examples/shop/scenarios.json` 中的命名场景，每个场景只比基线改一个参数，并给出业务理由 |
| 反事实故障分析 | 同一场景、同一租户的对照重复与处理重复（缺省各 3 次）由 `faultpoint.tools.analysis.compare` 比较，每个效果是一条边（原因故障 → 效果） |
| 分阶段预算分配 | 覆盖、轮转、加权三个阶段（第 2.2 节） |
| 因果等价故障 | 效果向量相近的故障聚成一簇，预算按簇分配 |
| 条件性因果 | 效果随场景变化的簇在加权阶段得到更多预算；每条边学到自己的激活条件 |
| 兼容性检查 | 拼接时合并各条边的参数条件，不能把同一个参数设成两个值 |
| 拼接 | 束搜索，排序键见第 2.3 节 |
| 验证 | 合并条件得到一个新负载，只注入链首故障，逐跳检查效果 |

这一层依赖两个前提：

- **条件可以学习**：负载参数是显式的，每条边的激活条件就是“这条边成立的场景共有、而在它不成立的被测场景中不同的参数值”，不必从代码路径推断两个负载能否同时成立。
- **链可以端到端验证**：我们控制被测系统，可以把链上各边的条件合并成一个负载，只注入链首故障，看每一跳的效果是否出现；拼接出的链不必停留在假设。

另有两点由 faultpoint 的性质决定：

- **效果与故障不是一一对应**：outcome 只是动作结果的一部分（例如超时不说明对端是否已完成，4xx 只保留状态类别），所以效果到故障的对应是一个数据文件，一个效果可以对应多个候选故障，也可以没有对应。
- **一次运行可以测多个故障**：被测系统按租户隔离数据，故障用 `fp.scope` 限定到各自的租户，不注入的租户用来发现越过租户的影响（第 2.1 节）。

## 2. 流程

`faultsearch explore|stitch|validate|report EXPERIMENT`，所有输入、运行、效果、边、簇、链和验证都以 JSON 保存在 `runs/search/EXPERIMENT/` 下。已有的记录在重新执行时直接读取，因此中断后可以续跑；输入（场景、动作表、效果映射、运行与分配设置）在第一次执行时记录，之后不同则拒绝执行，保证续跑的记录可比。服务用 `--sdk-root` 指定的 SDK 提交构建；`search` 按路径依赖 `../python`，它随仓库的其他工作变化，所以实验时把 `search` 环境中的 faultpoint 换成同一提交的 worktree（`uv pip install -e <worktree>/python[tools]`，之后用 `uv run --no-sync`），比较与观测解析也就来自这个提交。

### 2.1 反事实故障分析：对照、处理与打包

- **对照**：每个负载 3 次不注入的重复，按负载缓存。每次重复使用新的数据库，并在独立的网络命名空间中运行（`unshare --user --map-root-user --net`）：多个重复可以并行而端口不变，客户端故障点的 id 中含有对端地址，端口不变 id 才不变。
- **处理**：每个（故障，负载）3 次重复，与同一负载中同一租户的对照比较。故障在所有重复中都实际注入过才算被执行（exercised），未被执行的处理不参与边的统计。服务启动时若拒绝规则（各 SDK 在“处理该类故障点的插件并非都实现这个动作”时停止进程，消息为 `faultpoint: rule <id>: …`），这次重复记下拒绝的原因，故障视为未执行，实验继续。
- **时长上限**：一次重复最多发送 120 s 的结账，对照约 10 s 就发完全部结账。使所有租户共享的服务停住的故障（例如让 inventory 唯一的连接池失效），不加上限时每次重复要 500 s 以上；加上限后它的失败仍在前 120 s 中出现，只是后面的结账不再发送。
- **打包**：负载有 4 个租户，各租户的 SKU 和账户互不相交，负载按 a、b、c、d 轮流发出请求。非延迟故障每 2 个一组，限定在租户 a 和 c，b 和 d 不注入作为哨兵，使每个被注入租户的下一个请求都属于哨兵：orders 中未处理的异常会让紧接着的下一个请求在 gateway 的 fetch 处失败（见第 4.3 节），这种越界只落在下一个请求上，哨兵只放在最后会漏掉它。任一哨兵与自己的对照有差异，这一组的故障就各自单独重跑，原组记在 `leaks/`。延迟故障从一开始就单独运行：延迟通过租户共享的东西起作用（inventory 唯一的数据库连接、ledger 的同步方法、orders 和 gateway 的事件循环、顺序发出的负载本身），越过租户是它的常态，先打包再重跑只会多花时间。单独运行时只注入租户 a，其他三个租户的差异记录在处理记录的 `leakage` 中。
- **效果**：`compare` 的 `min_mean_increase` 在搜索中取 0.5：注入本身的开销能让亚毫秒级的均值显著增加两三成（pricing 的 `negate` 使 `GET /price/{}` 的均值从 0.026 ms 增加到 0.033 ms），而目录中的延迟是 500 ms，均值的真实变化远大于一倍。

### 2.2 分阶段预算分配

预算是（故障，场景）对的个数，包括第一阶段。

1. **覆盖**：每个故障注入一次，场景取对照中该故障点在租户范围内执行次数最多的场景，次数相同时取场景文件中靠前的场景（基线在最前），使第一阶段的效果向量尽量来自同一负载、彼此可比。效果向量是 IDF 加权的效果指示向量；用 scipy 的平均连接层次聚类按余弦距离（阈值 0.5）把故障分成因果等价的簇。没有效果的运行彼此相似度为 1，与有效果的运行相似度为 0。
2. **轮转**：剩余预算的一半在各簇间轮转，每次取簇中随机一个成员，注入一个它没去过、且执行它的故障点的场景。
3. **加权**：其余预算按簇的权重 max(ε, 1 − 簇内相似度) 抽样（ε = 0.05），每批 18 个后重新计算权重。簇内相似度是簇内成员全部运行的效果向量两两余弦相似度的平均，效果随场景变化的簇（条件性因果）权重高。

随机分配用同样的预算，从所有“故障 × 执行该故障点的场景”中均匀抽样。两种分配的同一个（故障，场景）对共用一份处理记录。

### 2.3 边、条件与拼接

- **边**：（原因故障，效果 = 故障点、outcome、指标），记录成立的场景（及每个场景的比较结果）和测试过但不成立的场景。计数的增加至少要达到对照的 `--min-count-increase`（取 0.2，与 `faultpoint diff` 对均值的缺省一致）才算效果：范围之外的计数（上游组件的系统调用、后台工作）随运行时长增长，两组各自恒定时比较不做检验，没有这个下限，多 1 次就成了效果。在第二轮的记录中，上游层的计数增加有 694 次低于 20%（587 次低于 5%），其余层的计数增加 94% 不低于 20%。同一下限也用于判断端到端可见和验证中的每一跳。
- **条件**：在成立场景共有的参数值中，贪心地选出最少的一组，使每个不成立的被测场景至少在一个参数上不同；边没有在基线成立时，基线也必须被区分开，因为没有证据表明它在基线上成立。找不到这样一组值时（例如只在 limited-stock 和 strict-timeout 两个场景成立），条件是析取的，每个成立场景的改动各是一个选项。
- **拼接**：一条边的效果对应的故障，作为下一条边的原因。束搜索（最多 4 跳）从每条有对应故障的边出发，扩展时合并条件，冲突即剪枝；回到链首故障的记为环。每个长度只扩展尚未终止于用户可见失败的链，按需要多个场景、跨越的服务数和簇内相似度保留最前的 20000 条：已经终止的链是完整的，若让它们按完整排序占据束，还差一跳才终止的链会被挤掉。shop 的图在这个宽度下等于穷举 4 跳以内的全部链（宽度 5000 时链数已经相同）。
- **排序**：依次比较需要多个场景（没有一个被测场景中每一跳都成立）、跨越的服务数（不计上游组件：它们的后台工作只因运行变长就增加）、是否终止于用户可见的失败（gateway 的 `rpc_server` 非 2xx）、簇序列的新颖性（排在前面的链没有相同的簇序列）、各跳所在簇的簇内相似度的平均。
- **端到端可见**：在某个被测场景中，只注入链首故障的那次处理已经显示了每一跳的效果，这条链就是单场景可见的；否则只能靠拼接得到。

### 2.4 验证

对排名最前的只靠拼接得到的链（缺省 10 条）和几条单场景可见的链（缺省 3 条），把条件合并到基线上得到负载 `validate.<参数=值>`，在其中只注入链首故障（单独运行，3 次对照、3 次处理），逐跳检查效果是否出现。链首故障和合并负载相同的链共用一次运行。`--cross-layer` 另外验证排名最前的、跨越多个层的只靠拼接的链。`--chain` 按键另外验证排序之外的链（也可以是以前验证过的链），记录中标为 `named`，与按排序选出的验证分开报告。

验证反馈到效果映射：一跳的效果出现时，看下一跳的效果是否随之出现，记为对（效果，对应的故障，下一跳期待的后果）这一步的一次证实或否定，累积在 `mapping-feedback.json` 中。只被否定、从未被证实的步，拼接不再经过。单位是三元组而不是（效果，对应的故障）：同一个对应可以带来一个后果而带不来另一个，例如把 orders 的 `retryable` 取反带来了更多的重试和用户的 5xx，却带不来“每次重试都再预留一次”。

### 2.5 故障来源与层

一次重复中有几个故障来源，它们读同一个规则文件，各自安装属于自己的故障点的规则，并把观测以共同的格式写进重复的目录：

| 来源 | 故障点 | 范围 |
| --- | --- | --- |
| 业务代码中的 SDK 故障点 | 各服务的进程内故障点和边界故障点 | 按租户（`fp.scope`） |
| 依赖库中的 SDK 故障点 | 配置的 `placement.scope` 列入的库：orders 的 `redis.asyncio`，inventory 的 `pgxpool` 与 `puddle`；先跑不带规则的对照，只有执行过的故障点进入目录 | 按租户 |
| 内核代理 | 上游组件容器的系统调用（`syscall`）和发出的网络包（`packet`） | 整个容器 |

部署负责每个来源的生命周期：每次重复启动新的 Redis 和 PostgreSQL 容器，再在一个特权容器中启动只服务这两个容器的 eBPF 代理，然后在重复自己的网络命名空间中启动 shop 的服务；slirp4netns 把这个命名空间接到宿主机，服务经 10.0.2.2 访问容器发布在宿主机回环上的端口。Redis 和 PostgreSQL 的故障点 id 不含服务端地址，所以每次重复的端口不同也不改变 id。代理停止时卸下它装上的程序；它的观测留在它自己的容器里，停止后再复制出来，因此不会有属于 root 的文件留在重复目录中。

- **范围之外的故障**：内核看不到请求的 baggage，`syscall` 和 `packet` 的规则不带范围，作用于所有租户，因此这类故障单独运行，没有哨兵，由第一个租户代表全部租户。这类故障作用于整个容器或进程，边和链的每一跳都记下它作用的对象（由部署给出，例如“postgres 容器（postgres:16）”），使从上游容器进入服务的那一跳在链中明确可见。
- **范围之外的效果**：上游组件的系统调用、服务的后台工作都在范围之外（`fp.scope` 为空）。每次处理除了比较被注入的租户，还比较范围之外的观测；只有单独运行的故障才能把这部分效果归于它，所以带上游组件的实验不打包（`--no-pack-tenants`）。
- **配置的故障点**：代理只观测它注入的网络包，`packet` 故障点不会出现在对照中，由部署列出（`shop.upstream.PACKET_POINTS`），视为在每个场景中都执行。
- **层**：上游组件（`redis`、`postgres`）的故障点属于上游层；业务服务的 `syscall`、`packet` 属于内核层；id 中带库名与版本（`<库>@<版本>/…`）的属于依赖库层；其余属于业务层，包括业务服务调用依赖的边界故障点。每条边记下原因故障和效果所在的层，每条链记下各跳故障的层和最后效果的层，报告按层的序列统计。

## 3. 数据文件

### 3.1 场景：`examples/shop/scenarios.json`

基线：4 个租户，每个 SKU 库存 1000，每个账户余额 100000，SKU 为 1、2、7，数量按 1、2 交替，orders 客户端超时 2 s，价格在 Redis 中缓存 60 s。每个租户顺序发出 21 次结账，各租户交替。

| 场景 | 改动 | 业务理由 |
| --- | --- | --- |
| `baseline` | — | 普通经营：库存和余额都充足 |
| `limited-stock` | 库存 12 | 小门店每样商品只备一打，略多于一个租户订单所需的 10 到 11 件 |
| `tight-budget` | 余额 3300 | 预付账户只比通常订单金额（2982）多一成，不够支付贵四分之一的价格 |
| `strict-timeout` | 超时 0.3 s | 移动端结账要求请求很短，orders 给每次下游调用 0.3 s |
| `clearance-sale` | SKU 7、17、27 | 清仓只卖编号以 7 结尾、由 pricing 打折的商品 |
| `bulk-orders` | 数量 5、10 交替 | 批发客户按 5 件和 10 件成箱订购，不超过 gateway 的上限 10 |
| `fresh-prices` | 缓存 1 s | 改价期间，orders 只能把单价在缓存中保留一秒（只在第二轮） |

orders 的超时由环境变量 `RESERVE_TIMEOUT_S` 给出，作用于它的整个 httpx 客户端，所以 strict-timeout 也收紧了它对 pricing 和 ledger 的调用。第二轮中 orders 先查 Redis 中的单价（`GET price:<sku>`，0.25 s 超时），未命中或 Redis 出错时向 pricing 查询并写回（`SET … EX <TTL>`）；inventory 的库存在 PostgreSQL 中，经 pgxpool 只用一个连接访问。

### 3.2 动作表：`search/data/actions.json`

每类故障点尝试的动作。延迟统一为 500 ms，小于缺省超时 2 s，大于 strict-timeout 的 0.3 s：它表示依赖变慢而不是中断。

| 类别 | 动作 |
| --- | --- |
| `branch` `call` | `fail`，`delay` |
| `check` | `negate`，`delay` |
| `loop` | `delay` |
| `rpc_client` | `fail` 503，`fail` timeout，`fail_after` timeout，`duplicate`，`delay` |
| `rpc_server` | `fail` 503，`fail_after` 503，`delay` |
| `store_read` | `fail`，`empty`，`delay` |
| `store_write` | `fail`，`fail_after`，`drop`，`duplicate`，`delay` |
| `syscall` | `fail` EIO |
| `packet` | `delay` 500 ms |
| 依赖库中的 `branch` `call` `check` | `fail`、`fail`、`negate`，不延迟 |

不尝试 `crash`：它不能限定到租户，会结束整次运行。shop 中没有 `value`、`clock`、`acquire` 故障点，表中也就没有它们的动作；遇到表中没有的类别，故障点会被排除并给出原因。依赖库中的故障点多在热路径上，一次请求执行几十次，每次延迟 500 ms 测到的主要是延迟本身，依赖变慢已经由业务服务的边界故障点表达，所以库中不延迟，库中的 `loop` 也就没有动作。网络包不丢弃：全部丢弃使 TCP 停顿到客户端超时，测到的是超时；部分丢弃需要按概率触发，目录还不表达触发条件。

### 3.3 效果映射：`search/data/effects.json`

每条规则把（类别，outcome，指标，判定，所在的层）对应到同一故障点上的动作模板；目录中动作包含模板全部参数的故障就是候选。依赖库中的结果来自库所调用的东西，在库自己的故障点上注入同样的结果，可能使库进入自然结果不会进入的状态：在 pgxpool 的 `Acquire` 处注入的错误使 inventory 唯一的连接池失效、请求挂起，而上游故障引起的 `Acquire` 错误立刻返回。因此库中的结果不对应任何故障，拼接经过接收这个结果的业务调用点，后者的效果在同一次注入中同样出现。

| 效果 | 对应的故障 |
| --- | --- |
| `branch` taken | `fail` |
| `call` error | `fail` |
| `check` 出现对照中没有的结果 | `negate` |
| `loop` 迭代增加 | `delay`（解读为竞争） |
| `rpc_client` timeout | `fail` timeout 与 `fail_after` timeout 两个候选：超时不说明对端是否已经完成 |
| `rpc_client`/`rpc_server` 5xx | `fail` 503 |
| `rpc_client` refused | `fail` refused（不在目录中） |
| `rpc_client`/`rpc_server` 均值增加 | `delay` |
| `store_read` empty / error | `empty` / `fail` |
| `store_write` ok 增加 / error | `duplicate` / `fail` |
| `syscall` EIO | `fail` EIO |
| 依赖库中的 `branch` `call` `check` `loop` 的结果 | 无：拼接经过接收这个结果的业务调用点 |

没有可注入对应物的效果：`branch` not_taken、`call` ok、`store_read` rows 的增加只说明执行次数变多；`check` 已有结果的增加同样可能只是执行变多；`rpc_*` 的 2xx/3xx/4xx 增加，4xx 只保留状态类别，而调用方按具体状态码分支（orders 只把 409 当作缺货，其他 4xx 当作成功）；`rpc_*` error 没有命名的动作；存储每次执行的行数增加是数据的变化，没有存储动作产生它。入口服务（gateway）`rpc_server` 的 4xx、5xx、error 是用户可见的终点。

## 4. 第一轮结果：业务代码

证据范围：一次实验，`runs/search/shop-stitching/`；shop 还没有上游组件（inventory 与 ledger 用 sqlite，orders 不缓存价格，即提交 `18f6989` 之前的 shop），只有业务代码中的 SDK 故障点；SDK 提交 `bb5168d`，服务和 `faultsearch` 使用的 faultpoint 分析代码都来自这一提交的 worktree；每个负载 3 次对照、3 次处理；8 个部署并行，全部运行约 55 分钟。只有一个随机种子。每次运行的原始数字、每条边和每条链都在该目录中，本节只给结论和支撑它的计数。

### 4.1 规模

- 目录：34 个故障点、90 个故障。2 个故障点只在服务启动时执行、不在任何租户的范围内（inventory 的 `main` 中的 `call`、orders 建表的 `store_write`），被排除。
- 预算：每种分配 240 次注入，是全部 540 个（故障，场景）对的 44%。分阶段分配中覆盖 90 次（65 次落在 baseline；25 次落在 strict-timeout，因为冷启动的超时重试使 inventory 和 orders 重试路径上的故障点在那里执行得更多），轮转 75 次，加权 75 次。
- 重复：场景对照 18 次；两种分配的处理合计 1038 次；哨兵发现越界、改为单独重跑的打包组 12 组 36 次；验证 15 次对照、33 次处理。

### 4.2 边与条件

分阶段分配得到 665 条边：301 条有条件（某个被测场景中不成立），364 条无条件，其中 97 条的原因故障只测过一个场景，无条件只是因为没有反例。413 条边的效果有目录中的对应故障，252 条没有。

| 边 | 成立 | 不成立 | 学到的条件 |
| --- | --- | --- | --- |
| orders 对 `/reserve` 的 `fail_after` timeout → inventory 缺货分支 taken | limited-stock | 其余 5 个场景 | `stock_per_sku=12` |
| inventory `handleReserve` 写入之后的 `err != nil` 处延迟 → orders 对 `/reserve` 超时 | strict-timeout | clearance-sale、tight-budget、limited-stock | `reserve_timeout_s=0.3` |
| gateway 对 orders、orders 对 `/charge` 的 `duplicate` → gateway 4xx | tight-budget | 其余被测场景 | `balance=3300`（重复扣款耗尽余额） |
| inventory 库存写入的 `duplicate`、`fail_after` → gateway 4xx | limited-stock | strict-timeout、baseline 等 | `stock_per_sku=12` |
| inventory 各处延迟 → gateway 2xx 均值增加 | 2 s 超时的各场景 | strict-timeout（请求被取消，不是变慢） | 析取，例如 `sku_numbers=[7,17,27]` 或 `balance=3300` 或 `stock_per_sku=12` |

第一行是已知的正例：每次重试都真的完成了预留，有限的库存被耗尽。分阶段分配和随机分配都找回了它，条件都是 `stock_per_sku=12`。

分阶段分配把故障分成 18 个因果等价的簇。簇大体按服务和动作的语义聚合，例如 inventory 写入之后的延迟、orders `retryable` 取反、orders 对 `/reserve` 的 `fail_after` timeout 是同一簇（都使 inventory 完成预留而 orders 仍然重试）；第一个场景中没有任何效果的故障（gateway 入口的注入、写入的 `drop`/`duplicate`、pricing 的 `discounted` 取反等）聚成一簇。

### 4.3 越过租户的影响

- **冷启动**：strict-timeout 的对照中，没有任何注入，每个租户的第一个请求也会超时失败（冷启动比 0.3 s 慢），对照的计数在重复间因此有波动。注入使被注入的租户先失败，后面的租户不再碰上冷启动，哨兵因此与对照不同；strict-timeout 中形成的打包组（1 组）因此改为单独运行，这个场景的 75 条处理记录都来自单独运行。
- **下一个请求**：orders 中未处理的异常（`price()` 和 `charge()` 不处理 httpx 的传输错误，价格或扣款超时就以异常结束；写入 orders 表失败同样如此）之后，紧接着的下一个请求在 gateway 的 fetch 处失败（outcome `error`，用户得到 502），不论它属于哪个租户。被哨兵发现越界的 12 个打包组中，11 个是这种情形（baseline、clearance-sale 各 3 组，bulk-orders、tight-budget 各 2 组，limited-stock 1 组），另 1 个是上面的冷启动。机制未核实：可能是 uvicorn 在未处理的异常之后关闭连接，而 gateway 的 fetch 复用了这条连接。
- 越过租户的影响只记录在处理记录的 `leakage` 中，不形成边。

### 4.4 链与验证

分阶段分配的边拼出 11627 条 4 跳以内的链：8868 条只靠拼接得到，2759 条单场景可见；另有 26 个环。验证排名前 10 的只靠拼接的链和前 3 的单场景可见的链：

| 链（首故障 → … → 终点） | 选取 | 合并负载 | 结果 |
| --- | --- | --- | --- |
| inventory 写入库存之后延迟 500 ms → orders 超时并重试 → 缺货分支 → orders 409 → 用户 4xx | 只靠拼接，第 6 | strict-timeout + limited-stock | 证实 |
| inventory 写入之后返回错误 → `retryable` 为真 → 缺货 → 用户 4xx（4 条，中间跳不同） | 只靠拼接，第 1、2、3、10 | strict-timeout + limited-stock | 证实 |
| inventory 缺货分支处（写入之前）延迟 500 ms → 超时 → … → 用户 4xx 或 5xx（5 条） | 只靠拼接，第 4、5、7、8、9 | strict-timeout（+ limited-stock 或 tight-budget） | 否定 |
| ledger 或 pricing 中延迟 500 ms → orders 的调用超时 → 用户 5xx（3 条） | 单场景可见 | strict-timeout | 证实 |

- **设想的链得到证实**：第一跳只在 strict-timeout 成立，第二跳只在 limited-stock 成立，没有一个被测场景显示全链。在合并负载中只注入链首的延迟，租户 a 的 21 次结账中 13 次缺货（409）、8 次 502，3 次重复完全相同；对照中全部是 201。inventory 写入完成后才变慢，orders 超时后重试，每次重试都再预留一次，库存被提前耗尽。
- **被否定的 5 条链都从写入之前的延迟出发**，否定的跳揭示了效果映射和条件的近似：
  - 超时的两个候选中实际成立的是 `fail` 而不是 `fail_after`：orders 超时断开后，Go 的请求上下文被取消，之后的数据库操作失败，预留没有发生（库存写入没有增加），缺货分支从未执行。
  - inventory 的错误（`handleReserve` 中 `err != nil` 为真）发生在 orders 已经超时离开之后，orders 看到的是超时，不是 5xx，“error → `fail` → 调用方 5xx”这一跳不成立。
  - “延迟使 `/reserve` 的 2xx 均值增加”只在超时为 2 s 的场景测到成立，学到的析取条件不含“超时仍是 2 s”，与 strict-timeout 合并后这一跳不成立。单参数的场景说明不了一条边在某个场景中不成立是因为哪个参数。
- 26 个环（例如 `retryable` 取反 → 库存写入增加 → `duplicate` → `/reserve` 均值增加 → 延迟 → `err != nil` 为真 → `fail` → `retryable` 为真）没有验证。

### 4.5 比较

**随机分配**（同样 240 次注入、同一种子）：

- 552 条边，其中 150 条有条件（分阶段分配为 665 和 301）。两者共有 483 条；只有分阶段分配找到的 182 条中 179 条有条件，只有随机分配找到的 69 条中 66 条有条件。分阶段分配在轮转和加权阶段把预算给了效果随场景变化的簇，多出来的几乎都是有条件的边。
- 只靠拼接、终止于用户可见失败的链：分阶段分配 784 条，随机 243 条；环 26 个对 0 个。
- 5 条证实的链，随机分配的边和链也都有：在 shop 这样的规模上，均匀抽取 44% 的（故障，场景）对已经覆盖了它们。5 条被否定的链，随机分配都没有（它没有在 strict-timeout 中注入缺货分支处的延迟）。

**单场景**：不拼接时，各场景的单次注入已经显示的（首故障，用户可见失败）对：baseline 36、strict-timeout 44、limited-stock 22、tight-budget 16、clearance-sale 15、bulk-orders 8，合计 69 个不同的对。分阶段分配只靠拼接、终止于用户可见失败的链覆盖 59 个这样的对，其中 33 个没有任何单次注入显示过。设想的链属于这 33 个：inventory 写入之后的延迟在 strict-timeout 中只让用户看到 5xx，在 limited-stock 等超时为 2 s 的场景中只使响应变慢，缺货的 4xx 只在合并负载中出现。

### 4.6 负面发现

- **值的变化没有观测点**：pricing 的 `discounted` 取反在 baseline、bulk-orders、strict-timeout 中测过，除了 strict-timeout 中冷启动的预热（第 4.3 节）没有任何效果：价格变了，但没有故障点观测价格。按代码中的价格计算，clearance-sale 的 SKU 全部打折，取反后每个租户的总价从 2883 升到 3627，超过 tight-budget 的余额 3300，ledger 会拒绝付款；这一组合没有运行。这条边不会出现，任何拼接都找不到经过它的链；要找到它，需要在价格计算上人工标注 `value` 故障点。
- **只能做终点的效果**：252 条边的效果没有可注入的对应故障，主要是执行次数的增加和 4xx 状态类别，它们只能结束一条链。
- **orders 的传输错误处理**：`price()` 和 `charge()` 不捕获 httpx 的传输错误，下游超时以未处理的异常（500）结束，而 `reserve()` 会重试；这是 shop 的业务代码本身的行为，并引出了第 4.3 节的越界。

## 5. 第二轮结果：业务代码、依赖库与上游组件

证据范围：一次实验，`runs/search/shop-layers/`；shop 带 Redis 价格缓存和 PostgreSQL 库存（提交 `18f6989` 起）；SDK 提交 `3b6a082`，服务和 `faultsearch` 使用的 faultpoint 都来自这一提交的 worktree；每个故障单独运行，每个负载 3 次对照、3 次处理；8 个部署并行，探索分三段运行，后两段沿用前面已完成的重复，连同验证共约 82 分钟（边和链从已有记录推导，三轮验证反馈新增的只有验证运行，约 7 分钟）。只做了分阶段分配，没有随机分配的对照。

### 5.1 规模

- 目录：182 个故障，业务层 136 个、依赖库层 37 个、上游层 9 个（PostgreSQL 的 `fdatasync` `pwrite64` `read` `recvfrom` `sendto` 与 Redis 的 `read` `write` 返回 EIO，两个容器发出的包延迟 500 ms）。依赖库中放置的点有 507 个从未在租户范围内执行，被“先观测、再注入”排除；库中的 5 个 `loop` 没有动作。
- 预算：360 次注入，是全部 1274 个（故障，场景）对的 28%：覆盖 182 次，轮转 89 次，加权 89 次。上游故障除覆盖外只再得到 1 次注入，多数只在一个场景中测过。
- 拒绝：ledger 的 Java agent 拒绝了它的 JDBC `store_write` 点上的 `duplicate` 和 `fail_after`（服务这类点的插件并非都实现这两个动作），这两个故障记为未执行，其余 357 次注入都实际执行了。

### 5.2 跨层的传播

上游故障单次注入就能显示跨越三层的传播：

| 上游故障 | 依赖库中的效果 | 业务层与用户 |
| --- | --- | --- |
| PostgreSQL 的 `read` `pwrite64` `fdatasync` `sendto` `recvfrom` 返回 EIO | pgxpool 的 `Acquire`、`QueryRow` 出错，puddle 建立资源（`initResourceValue`）出错，`fdatasync` 时连连接的建立都失败 | inventory 的错误分支，用户每次结账都得到 502 |
| PostgreSQL 发出的包延迟 500 ms | pgxpool 的 `Acquire` 出错 | 120 s 内每个租户只发出 5 次结账，全部 502 |
| Redis 的 `read` `write` 返回 EIO | redis-py 重试（`Retry.call_with_retry` 分支走入重试）、重新连接、`get_connection` 出错 | orders 的 `cached_unit` 和 `remember_unit` 捕获错误并回退到 pricing，用户仍然成功 |
| Redis 发出的包延迟 500 ms | 同上（0.25 s 的缓存超时） | 用户成功，结账均值从约 105 ms 升到约 630 ms |

依赖库层和上游层上共有 85 种效果，其中 20 种是依赖库中错误一类的结果（pgxpool、puddle、redis-py 中调用出错、重试分支走入）；业务层的故障点只能看到 inventory 返回 500 或 orders 的缓存回退，看不到失败发生在连接池建立连接、取连接还是重试的哪一步。2608 条边中，原因与效果跨层的有 1180 条：依赖库→业务 418、业务→依赖库 363、上游→业务 125、业务→上游 123、上游→依赖库 113、依赖库→上游 38。

### 5.3 链与验证

2608 条边（573 条有条件）。计数下限去掉了 631 条只靠小幅计数增加成立的边，其中 531 条的效果是上游组件的系统调用计数（例如 PostgreSQL 的 `fdatasync` 在 3 次对照中都是 84 次、在 3 次处理中都是 85 次）；依赖库的规则使 260 条边的效果不再对应任何故障。在三轮验证反馈之后，拼接出 39825 条 4 跳以内的链：23024 条只靠拼接得到，16801 条单场景可见；2 个环。反馈累积了 74 次检查，涉及 33 步，其中 23 步只被否定过，拼接不再经过。宽度 20000 的束在这个规模上不是穷举。

验证都在合并负载中只注入链首故障，3 次对照、3 次处理：

| 选取 | 条数 | 证实 | 否定 |
| --- | --- | --- | --- |
| 反馈的起点：不计数下限时排名最前的只靠拼接的链（10 条）、单场景可见的链（3 条）、跨层的只靠拼接的链（8 条），按现在的规则逐跳复核 | 21 | 0 | 21 |
| 跨层、只靠拼接、终止于用户可见失败、在每轮反馈后排名最前的链，三轮各 10 条 | 30 | 0 | 30 |
| 跨层、单场景可见、终止于用户可见失败的链（阳性对照，按键指定，每轮复核） | 3 | 3 | 0 |

- **没有一条只靠拼接的跨层链被证实。**
- **证实的跨层链**：PostgreSQL 的 `recvfrom` 返回 EIO（作用于 postgres 容器）→ pgxpool `Acquire` 出错 →（pgxpool `QueryRow` 出错 →）orders 的 `retryable` 为真，或 orders 对 `/reserve` 的调用收到 5xx → 用户 5xx。层的序列是上游 > 依赖库 >（依赖库 >）业务 > 业务，每轮复核都是每一跳都出现。它们是单次注入就显示的传播，不需要拼接；依赖库中的结果不再对应故障之后，拼接不再产生这三条链，同一传播经由 inventory 的业务调用点出现。
- **只靠拼接的跨层链被否定的原因**：每一处拼接都把上一跳引起的结果换成在同一故障点上注入的同一结果；在 shop 中，只看结果说明不了接下来会发生什么。验证记录中的三种情形：
  - **重试之前有没有完成工作**：前两轮的 20 条链都经过“`retryable` 为真 → 把 `retryable` 取反”。取反让 orders 重试已经成功的预留，每次重试都再预留一次，在 limited-stock 中耗尽库存；而链首（上游的 EIO、在 pgxpool 内部注入的失败）使 inventory 在写入之前就失败，重试不消耗库存，缺货分支和库存写入的增加都没有出现。按三元组的反馈排除了被否定的后果（缺货分支），搜索随即找到同一个对应的另一个后果（库存写入增加），也被否定。这与第一轮“超时不说明对端是否已完成”是同一类问题。
  - **异常的类型**：在 redis-py 内部注入的失败抛出的异常越过了 orders 的 `create_order` 中的处理器（`create_order` 的调用出错），用户得到 502；拼接把这一结果对应到在这个调用点上注入 `fail`，而 SDK 在 Python 调用点上抛出处理器列出的第一个异常类，这里是 `OutOfStock`，用户得到 409。
  - **错误是否在调用方的超时之前到达**：PostgreSQL 的包延迟下，inventory 在 3 次处理中每次都返回 15 次 5xx，orders 对 `/reserve` 的调用每次也都有 15 次超时：错误在 orders 超时之后才到达，orders 不读状态码就重试，`retryable` 不会因此为真；拼接把 inventory 的错误对应到在它的调用点上注入 `fail`，后者立刻返回 5xx。
  - 这三种区别（工作是否已完成、异常的类型、错误相对于超时的时机）都不在观测的 outcome 中，效果映射也就无从区分。
- 已知的正例（`/reserve` 的 `fail_after` 超时耗尽有限的库存）在第二轮的分配中没有被注入到 limited-stock，这一边没有出现；改用 PostgreSQL 之后它仍然成立：用 SDK `3b6a082` 和提交 `18f6989` 的 shop，`examples/shop/experiment.py` 在 limited-stock 中运行 2 次对照、2 次处理，租户 a 的缺货分支每次 37 次（`runs/shop/experiment-3b6a082.out`）。

### 5.4 没有做的

- 用内核 uprobe 在 redis-server 等上游进程的函数上注入（第 6.5 节）：需要私有的镜像层、按 cgroup 过滤并在之后核实卸载，这一轮没有做。
- shop 服务自身的系统调用故障：`systemd-run --user --scope` 可用，但服务是在每次重复的用户命名空间里启动的，还没有把每个服务放进自己的子 cgroup。
- 第二轮没有做随机分配的对照。

## 6. 局限

- 一次实验、一个随机种子；随机分配与分阶段分配的比较只针对第一轮的这一次抽样。
- 计数的下限是固定的 20%：上游后台工作随运行时长的增加大多在 5% 以内，被它去掉；低于 20% 的真实增加（例如 33 次 Redis 命令多出 3 次）也被去掉。按运行时长归一化范围之外的计数，可以不靠这个下限。
- 效果映射只按故障点和 outcome 对应：工作是否已完成、异常的类型、错误相对于调用方超时的时机都不在 outcome 中，注入的结果因此可能与自然的结果走向不同（第 5.3 节）。依赖库中的结果已不再对应故障；业务层的调用点仍有这三种差别。
- 验证反馈按（效果，对应的故障，后果）三元组排除被否定的步，同一个不忠实的对应可以经由下一个后果再次出现；反馈只能逐步收敛，不能推广到同一类对应。
- 依赖库中的热路径故障点没有延迟动作；库中的 `fail` 可能使连接池进入真实系统不会进入的状态，结论限于它实际表现出的行为。
- 一次重复最多发送 120 s 的结账，使整个服务停住的故障只观测到前 120 s。
- 条件只从单参数场景学习：分不清一条边在某个场景中不成立是因为哪个参数，析取条件合并时可能丢掉必要的基线值（第 4.4 节被否定的第三类链）。原因故障只测过一个场景的边，条件只是把那个场景与基线区分开。
- 效果到故障的映射是近似：超时同时给出 `fail` 和 `fail_after`，验证才能分辨；4xx 丢失具体状态码；均值增加一律对应 500 ms 的延迟，幅度没有学习。目录中的延迟只有 500 ms 一种幅度。
- 打包只能发现越过到哨兵租户的影响；哨兵与被注入租户交替排列，覆盖“影响下一个请求”和“影响之后所有请求”两种情形，其他形状的越界会漏掉。
- 越过租户的影响不形成边；环没有验证。
- 束搜索在 shop 的图上等于穷举；更大的系统需要有限的束宽，排序和剪枝的取舍还没有在那种规模上检验。
- 排名前 10 的只靠拼接的链有一半被否定，被否定的都经过“写入之前的延迟 → 超时”这一跳；排序没有利用这种按效果映射近似程度区分可信度的信息。
