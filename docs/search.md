# 因果拼接搜索

`search/` 中的 `faultsearch` 在 faultpoint 的故障点之上做因果拼接：在多个已有的工作负载中各注入一个故障，用反事实故障分析比较注入与对照得到因果边，再把在不同工作负载中观察到的边拼接成跨越多个激活条件的传播链，并在合并的负载中端到端验证。`examples/shop` 是它的第一个被测系统。本文说明这一层的思路、它用到的数据文件，以及在 shop 上的初步结果。

## 1. 思路

级联故障需要多步传播，每一步由自己的条件激活。往往没有哪一个已有的工作负载同时满足所有条件，但每一步都能在某个更宽松的负载中单独触发。因此在许多负载中各注入一个故障，记录注入引起的额外故障，再把这些边拼接起来。

| 概念 | 本层的做法 |
| --- | --- |
| 故障与观测的共同词汇 | 故障是（故障点，动作），观测是（故障点，outcome，指标）；两者通过效果映射（第 3.3 节）对应 |
| 已有的工作负载 | `examples/shop/scenarios.json` 中的命名场景，每个场景只比基线改一个参数，并给出业务理由 |
| 反事实故障分析 | 同一场景、同一租户的对照重复与处理重复（缺省各 3 次）由 `faultpoint.tools.analysis.compare` 比较，每个效果是一条边（原因故障 → 效果） |
| 分阶段预算分配 | 覆盖、轮转、加权三个阶段（第 2.2 节） |
| 因果等价故障 | 效果向量相近的故障聚成一簇，预算按簇分配 |
| 条件性因果 | 效果随场景变化的簇在加权阶段得到更多预算；每条边学到自己的激活条件 |
| 兼容性检查 | 拼接时合并各条边的参数条件，不能把同一个参数设成两个值 |
| 拼接 | 束搜索，排序键见第 2.3 节 |
| 验证 | 合并条件得到一个新负载，只注入链首故障，逐跳检查效果 |

这一层依赖两个前提：

- **条件可以学习**：负载参数是显式的，每条边的激活条件就是“这条边成立的场景共有、而在它不成立的被测场景中不同的参数值”，不必从代码路径推断两个负载能否同时成立。
- **链可以端到端验证**：我们控制被测系统，可以把链上各边的条件合并成一个负载，只注入链首故障，看每一跳的效果是否出现；拼接出的链不必停留在假设。

另有两点由 faultpoint 的性质决定：

- **效果与故障不是一一对应**：outcome 只是动作结果的一部分。观测的细节（`detail`）补上精确的状态码、错误类型、请求是否已完整发出、服务端答复时调用方是否已经离开，但不记录调用之前工作是否已经完成（第 6.2 节），所以效果到故障的对应是一个数据文件，一个效果可以对应多个候选故障，也可以没有对应。
- **一次运行可以测多个故障**：被测系统按租户隔离数据，故障用 `fp.scope` 限定到各自的租户，不注入的租户用来发现越过租户的影响（第 2.1 节）。

## 2. 流程

`faultsearch explore|replay|stitch|complete|validate|report EXPERIMENT`，所有输入、运行、效果、边、簇、链和验证都以 JSON 保存在 `runs/search/EXPERIMENT/` 下。已有的记录在重新执行时直接读取，因此中断后可以续跑；输入（场景、动作表、效果映射、运行与分配设置）在第一次执行时记录，之后不同则拒绝执行，保证续跑的记录可比。服务用 `--sdk-root` 指定的 SDK 提交构建；`search` 按路径依赖 `../python`，它随仓库的其他工作变化，所以实验时把 `search` 环境中的 faultpoint 换成同一提交的 worktree（`uv pip install -e <worktree>/python[tools]`，之后用 `uv run --no-sync`），比较与观测解析也就来自这个提交。

### 2.1 反事实故障分析：对照、处理与打包

- **对照**：每个负载 3 次不注入的重复，按负载缓存。每次重复使用新的数据库，并在独立的网络命名空间中运行（`unshare --user --map-root-user --net`）：多个重复可以并行而端口不变，客户端故障点的 id 中含有对端地址，端口不变 id 才不变。
- **处理**：每个（故障，负载）3 次重复，与同一负载中同一租户的对照比较。故障在所有重复中都实际注入过才算被执行（exercised），未被执行的处理不参与边的统计。服务启动时若拒绝规则集（以 faultpoint 的停止码 70 退出；“处理该类故障点的插件并非都实现这个动作”时消息为 `faultpoint: rule <id>: …`，其他情形记下服务日志的最后三行），这次重复记下拒绝的原因，故障视为未执行，实验继续。规则可以指名 orders 模块中的异常类：SDK 载入规则时经它的导入钩子导入这个类，所以 orders 自己的目录也在它的 `PYTHONPATH` 上。
- **时长上限**：一次重复最多发送 120 s 的结账，对照约 10 s 就发完全部结账。使所有租户共享的服务停住的故障（例如让 inventory 唯一的连接池失效），不加上限时每次重复要 500 s 以上；加上限后它的失败仍在前 120 s 中出现，只是后面的结账不再发送。
- **打包**：负载有 4 个租户，各租户的 SKU 和账户互不相交，负载按 a、b、c、d 轮流发出请求。非延迟故障每 2 个一组，限定在租户 a 和 c，b 和 d 不注入作为哨兵，使每个被注入租户的下一个请求都属于哨兵：orders 中未处理的异常会让紧接着的下一个请求在 gateway 的 fetch 处失败（见第 4.3 节），这种越界只落在下一个请求上，哨兵只放在最后会漏掉它。任一哨兵与自己的对照有差异，这一组的故障就各自单独重跑，原组记在 `leaks/`。延迟故障从一开始就单独运行：延迟通过租户共享的东西起作用（inventory 唯一的数据库连接、ledger 的同步方法、orders 和 gateway 的事件循环、顺序发出的负载本身），越过租户是它的常态，先打包再重跑只会多花时间。单独运行时只注入租户 a，其他三个租户的差异记录在处理记录的 `leakage` 中。
- **效果**：`compare` 的 `min_mean_increase` 在搜索中取 0.5：注入本身的开销能让亚毫秒级的均值显著增加两三成（pricing 的 `negate` 使 `GET /price/{}` 的均值从 0.026 ms 增加到 0.033 ms），而目录中的延迟是 500 ms，均值的真实变化远大于一倍。

### 2.2 分阶段预算分配

预算是（故障，场景）对的个数，包括第一阶段。

1. **覆盖**：每个故障注入一次，场景取对照中该故障点在租户范围内执行次数最多的场景，次数相同时取场景文件中靠前的场景（基线在最前），使第一阶段的效果向量尽量来自同一负载、彼此可比。效果向量是 IDF 加权的效果指示向量；用 scipy 的平均连接层次聚类按余弦距离（阈值 0.5）把故障分成因果等价的簇。没有效果的运行彼此相似度为 1，与有效果的运行相似度为 0。
2. **轮转**：剩余预算的一半在各簇间轮转，每次取簇中随机一个成员，注入一个它没去过、且执行它的故障点的场景。
3. **加权**：其余预算按簇的权重 max(ε, 1 − 簇内相似度) 抽样（ε = 0.05），每批 18 个后重新计算权重。簇内相似度是簇内成员全部运行的效果向量两两余弦相似度的平均，效果随场景变化的簇（条件性因果）权重高。

随机分配用同样的预算，从所有“故障 × 执行该故障点的场景”中均匀抽样。两种分配的同一个（故障，场景）对共用一份处理记录。

- **重放**：`replay NEW --source OLD` 用新的 SDK 构建，在另一个实验的场景和设置下重跑它分阶段分配的全部（故障，场景）对，再把目录中这些分配没有覆盖的故障（例如新的故障来源）各注入一次；簇由每个故障的第一次运行重新计算。同一实验只用一个构建。
- **对应故障**：`complete` 把边的效果所对应、但还没有任何分配注入过的故障（多数是细节给出的状态码或错误类型），在这个效果成立的每个场景中注入一次，记为 `counterpart` 阶段，使拼接能经过它们；`stitch` 先报告还需要多少次这样的注入。

### 2.3 边、条件与拼接

- **边**：（原因故障，效果 = 故障点、outcome、细节、指标），记录成立的场景（及每个场景的比较结果）和测试过但不成立的场景。计数的增加至少要达到对照的 `--min-count-increase`（取 0.2，与 `faultpoint diff` 对均值的缺省一致）才算效果：范围之外的计数（上游组件的系统调用、后台工作）随运行时长增长，两组各自恒定时比较不做检验，没有这个下限，多 1 次就成了效果。在第二轮的记录中，上游层的计数增加有 694 次低于 20%（587 次低于 5%），其余层的计数增加 94% 不低于 20%。同一下限也用于判断端到端可见和验证中的每一跳。
- **条件**：在成立场景共有的参数值中，贪心地选出最少的一组，使每个不成立的被测场景至少在一个参数上不同；边没有在基线成立时，基线也必须被区分开，因为没有证据表明它在基线上成立。找不到这样一组值时（例如只在 limited-stock 和 strict-timeout 两个场景成立），条件是析取的，每个成立场景的改动各是一个选项。
- **拼接**：一条边的效果对应的故障，作为下一条边的原因。束搜索（最多 4 跳）从每条有对应故障的边出发，扩展时合并条件，冲突即剪枝；回到链首故障的记为环。每个长度只扩展尚未终止于用户可见失败的链，按需要多个场景、跨越的服务数和簇内相似度保留最前的 20000 条：已经终止的链是完整的，若让它们按完整排序占据束，还差一跳才终止的链会被挤掉。shop 的图在这个宽度下等于穷举 4 跳以内的全部链（宽度 5000 时链数已经相同）。
- **排序**：依次比较需要多个场景（没有一个被测场景中每一跳都成立）、跨越的服务数（不计上游组件：它们的后台工作只因运行变长就增加）、是否终止于用户可见的失败（gateway 的 `rpc_server` 非 2xx）、簇序列的新颖性（排在前面的链没有相同的簇序列）、各跳所在簇的簇内相似度的平均。
- **端到端可见**：在某个被测场景中，只注入链首故障的那次处理已经显示了每一跳的效果，这条链就是单场景可见的；否则只能靠拼接得到。

### 2.4 验证

对排名最前的只靠拼接得到的链（缺省 10 条）和几条单场景可见的链（缺省 3 条），把条件合并到基线上得到负载 `validate.<参数=值>`，在其中只注入链首故障（单独运行，3 次对照、3 次处理），逐跳检查效果是否出现。链首故障和合并负载相同的链共用一次运行。`--cross-layer` 另外验证排名最前的、跨越多个层、终止于用户可见失败的只靠拼接的链，其中第一个故障所在的层与最后的效果都相同的链最多取 `--per-pair` 条（缺省 3），使选出的链不集中在一个枢纽上；拼接为此分别保留排名最前的 300 条只靠拼接的和 300 条单场景可见的这类链。`--chain` 按键另外验证排序之外的链（也可以是以前验证过的链），记录中标为 `named`，与按排序选出的验证分开报告。

验证反馈到效果映射：一跳的效果出现时，看下一跳的效果是否随之出现，记为对（效果，对应的故障，下一跳期待的后果）这一步的一次证实或否定，累积在 `mapping-feedback.json` 中。只被否定、从未被证实的步，拼接不再经过。单位是三元组而不是（效果，对应的故障）：同一个对应可以带来一个后果而带不来另一个，例如把 orders 的 `retryable` 取反带来了更多的重试和用户的 5xx，却带不来“每次重试都再预留一次”。

### 2.5 故障来源与层

一次重复中有几个故障来源，它们读同一个规则文件，各自安装属于自己的故障点的规则，并把观测以共同的格式写进重复的目录：

| 来源 | 故障点 | 范围 |
| --- | --- | --- |
| 业务代码中的 SDK 故障点 | 各服务的进程内故障点和边界故障点 | 按租户（`fp.scope`） |
| 依赖库中的 SDK 故障点 | 配置的 `placement.scope` 列入的库：orders 的 `redis.asyncio`，inventory 的 `pgxpool` 与 `puddle`；先跑不带规则的对照，只有执行过的故障点进入目录 | 按租户 |
| 内核代理 | 上游组件容器的系统调用（`syscall`）和发出的网络包（`packet`） | 整个容器 |
| 内核代理的原生函数点 | 上游组件进程中的函数，由 uprobe 放置：Redis 的 `lookupKey`（只在读查找时注入“未找到”，写查找找不到会触发 Redis 自己的断言）和 PostgreSQL 的 `pq_getbyte`（EOF，它的 5 个调用处都把 EOF 当作客户端离开处理）；配置在 `shop.upstream.NATIVE_FUNCTIONS` | 整个容器 |

部署负责每个来源的生命周期：每次重复启动新的 Redis 和 PostgreSQL 容器，再在一个特权容器中启动只服务这两个容器的 eBPF 代理，然后在重复自己的网络命名空间中启动 shop 的服务；slirp4netns 把这个命名空间接到宿主机，服务经 10.0.2.2 访问容器发布在宿主机回环上的端口。Redis 和 PostgreSQL 的故障点 id 不含服务端地址，所以每次重复的端口不同也不改变 id。代理停止时卸下它装上的程序；它的观测留在它自己的容器里，停止后再复制出来，因此不会有属于 root 的文件留在重复目录中。

- **范围之外的故障**：内核看不到请求的 baggage，`syscall` 和 `packet` 的规则不带范围，作用于所有租户，因此这类故障单独运行，没有哨兵，由第一个租户代表全部租户。这类故障作用于整个容器或进程，边和链的每一跳都记下它作用的对象（由部署给出，例如“postgres 容器（postgres:16）”），使从上游容器进入服务的那一跳在链中明确可见。
- **范围之外的效果**：上游组件的系统调用、服务的后台工作都在范围之外（`fp.scope` 为空）。每次处理除了比较被注入的租户，还比较范围之外的观测；只有单独运行的故障才能把这部分效果归于它，所以带上游组件的实验不打包（`--no-pack-tenants`）。
- **配置的故障点**：代理只观测它注入的网络包，`packet` 故障点不会出现在对照中，由部署列出（`shop.upstream.PACKET_POINTS`），视为在每个场景中都执行。原生函数点在每条返回指令处观测自然结果，和 SDK 的故障点一样“先观测、再注入”。
- **私有的文件**：uprobe 挂在文件的 inode 上，共享镜像层中的同一个文件会让所有使用它的容器都陷入。每个上游容器启动时先把被探测的二进制复制到自己的可写层（`cp` 后 `mv` 回原路径），再执行镜像原本的命令；文件内容和 build-id 不变，故障点 id 也不变。代理以 `--pid=host` 运行，经容器中进程的 `/proc/<pid>/root` 打开文件。
- **范围**：故障点能否限定到租户取决于类别和来源：上游组件中的点由内核代理服务，即使类别是 `call`，规则也不带范围，对照中按范围之外的观测计算它是否执行过。
- **层**：上游组件（`redis`、`postgres`）的故障点属于上游层；业务服务的 `syscall`、`packet` 属于内核层；id 中带库名与版本（`<库>@<版本>/…`）的属于依赖库层；其余属于业务层，包括业务服务调用依赖的边界故障点。每条边记下原因故障和效果所在的层，每条链记下各跳故障的层和最后效果的层，报告按层的序列统计。

## 3. 数据文件

### 3.1 场景：`examples/shop/scenarios.json`

基线：4 个租户，每个 SKU 库存 1000，每个账户余额 100000，SKU 为 1、2、7，数量按 1、2 交替，orders 客户端超时 2 s，价格在 Redis 中缓存 60 s。每个租户顺序发出 21 次结账，各租户交替。

| 场景 | 改动 | 业务理由 |
| --- | --- | --- |
| `baseline` | — | 普通经营：库存和余额都充足 |
| `limited-stock` | 库存 12 | 小门店每样商品只备一打，略多于一个租户订单所需的 10 到 11 件 |
| `tight-budget` | 余额 3300 | 预付账户只比通常订单金额（2982）多一成，不够支付贵四分之一的价格 |
| `strict-timeout` | 超时 0.3 s | 移动端结账要求请求很短，orders 给每次下游调用 0.3 s |
| `clearance-sale` | SKU 7、17、27 | 清仓只卖编号以 7 结尾、由 pricing 打折的商品 |
| `bulk-orders` | 数量 5、10 交替 | 批发客户按 5 件和 10 件成箱订购，不超过 gateway 的上限 10 |
| `fresh-prices` | 缓存 1 s | 改价期间，orders 只能把单价在缓存中保留一秒（只在第二轮） |

orders 的超时由环境变量 `RESERVE_TIMEOUT_S` 给出，作用于它的整个 httpx 客户端，所以 strict-timeout 也收紧了它对 pricing 和 ledger 的调用。第二轮中 orders 先查 Redis 中的单价（`GET price:<sku>`，0.25 s 超时），未命中或 Redis 出错时向 pricing 查询并写回（`SET … EX <TTL>`）；inventory 的库存在 PostgreSQL 中，经 pgxpool 只用一个连接访问。

### 3.2 动作表：`search/data/actions.json`

每类故障点尝试的动作。延迟统一为 500 ms，小于缺省超时 2 s，大于 strict-timeout 的 0.3 s：它表示依赖变慢而不是中断。

| 类别 | 动作 |
| --- | --- |
| `branch` `call` | `fail`，`delay` |
| `check` | `negate`，`delay` |
| `loop` | `delay` |
| `rpc_client` | `fail` 503，`fail` timeout，`fail_after` timeout，`duplicate`，`delay` |
| `rpc_server` | `fail` 503，`fail_after` 503，`delay` |
| `store_read` | `fail`，`empty`，`delay` |
| `store_write` | `fail`，`fail_after`，`drop`，`duplicate`，`delay` |
| `syscall` | `fail` EIO |
| `packet` | `delay` 500 ms |
| 依赖库中的 `branch` `call` `check` | `fail`、`fail`、`negate`，不延迟 |
| 上游组件的原生函数点 | 按函数：`lookupKey` 的 `fail` NULL，`pq_getbyte` 的 `fail` EOF；名字是代理配置中为这个函数定义的失败 |

不尝试 `crash`：它不能限定到租户，会结束整次运行。shop 中没有 `value`、`clock`、`acquire` 故障点，表中也就没有它们的动作；遇到表中没有的类别，故障点会被排除并给出原因。依赖库中的故障点多在热路径上，一次请求执行几十次，每次延迟 500 ms 测到的主要是延迟本身，依赖变慢已经由业务服务的边界故障点表达，所以库中不延迟，库中的 `loop` 也就没有动作。网络包不丢弃：全部丢弃使 TCP 停顿到客户端超时，测到的是超时；部分丢弃需要按概率触发，目录还不表达触发条件。

### 3.3 效果映射：`search/data/effects.json`

每条规则把（类别，outcome，指标，判定，所在的层，故障点的语言，细节）对应到同一故障点上的动作模板；故障点的语言和登记的错误取自列出它的清单，一个服务可以有几个清单（例如 SDK 的和原生挂钩点的），没有清单列出的故障点不适用按语言的规则。动作的参数可以取自细节（精确的状态码、错误类型）。目录中动作包含模板全部参数的故障就是候选；目录中没有的，作为故障保留下来，由对应故障阶段注入（第 2.2 节）。规则要求的细节键不在细节中时规则不适用：SDK 无法知道的键不写入细节（ledger 的 servlet 只在调用方已离开时写 `abandoned`，gateway 的 Node 服务端不记 `error`），缺少的键表示未知，不当作 false。客户端的规则还可以要求它调用的服务端点在同样的运行中有某种效果，服务端点由客户端点 id 中的端口和 `shop.deployment.PORTS` 得到。依赖库中的结果来自库所调用的东西，在库自己的故障点上注入同样的结果，可能使库进入自然结果不会进入的状态：在 pgxpool 的 `Acquire` 处注入的错误使 inventory 唯一的连接池失效、请求挂起，而上游故障引起的 `Acquire` 错误立刻返回。因此库中的结果不对应任何故障，拼接经过接收这个结果的业务调用点，后者的效果在同一次注入中同样出现。

| 效果 | 对应的故障 |
| --- | --- |
| `branch` taken | 无：`fail` 也在自然的原因到不了的执行中强制走入分支，例如成功的请求；拼接经过它背后的原因的边界效果 |
| `call` error（Python、Java、TypeScript、Rust 的服务） | `fail`，抛出细节中的错误类型，例如 Python 可导入的类；细节中没有类型时无对应 |
| `call` error（Go 的服务） | 无：Go 调用点的 `fail` 在被调用者执行之后、`err != nil` 的判断处替换错误，使已经完成的工作失败，自然的错误不会这样；已登记的哨兵在同一处判断，也一样 |
| `call` error（上游组件的原生函数，失败说明它的客户端已经离开，目前是 `pq_getbyte` 的 EOF） | 无：这是客户端行为的结果，忠实的对应是客户端自己的失败，链本来就能到达它 |
| `call` error（上游组件的其他原生函数，目前是 `lookupKey`） | `fail`，写入代理配置给出的、与自然失败相同的值 |
| `check` 出现对照中没有的结果 | 无：`negate` 翻转每一次判断，也翻转自然的原因没有碰到的执行，例如 orders 对已成功的预留判断 `retryable`；拼接经过它背后的原因的边界效果 |
| `loop` 迭代增加 | `delay`（解读为竞争） |
| `rpc_client` timeout，请求没有完整发出（`sent=false`） | `fail` timeout |
| `rpc_client` timeout，请求已发出，被调用的服务端在调用方离开后答复 2xx（`abandoned=true`） | `fail_after` timeout：对端完成了工作 |
| `rpc_client` timeout，请求已发出，服务端在调用方离开后答复 4xx 或 5xx | `fail` timeout：对端没有完成工作，`fail_after` 会让它完成 |
| `rpc_client` timeout，请求已发出，没有这样的服务端效果 | 无：不知道对端是否完成了工作 |
| `rpc_client`/`rpc_server` 4xx、5xx | `fail`，状态码取细节中的精确值：调用方按具体状态码分支（orders 只把 409 当作缺货） |
| `rpc_server` 在调用方离开之后答复（`abandoned=true`）的任何结果，次数或均值 | 无：这是服务端注意到调用方已超时，是调用方的结果；`abandoned` 不在细节中时是未知，按状态码和均值的那两行对应 |
| `rpc_client` refused | `fail` refused（不在目录中） |
| `rpc_client`/`rpc_server` 均值增加 | `delay` |
| `store_read` empty / error | `empty` / `fail` |
| `store_write` ok 增加 / error | `duplicate` / `fail` |
| `syscall` EIO | `fail` EIO |
| 依赖库中的 `branch` `call` `check` `loop` 的结果 | 无：拼接经过接收这个结果的业务调用点 |

规则可以按服务的清单区分已登记的错误：构建登记的错误名列在清单的 `errors` 中（inventory 的是 `shop/inventory.ErrOutOfStock` 和 puddle 的 `ErrClosedPool`、`ErrNotAvailable`），它们是构建的性质，不写在效果映射里。现在的映射没有用到它：只有 Go 调用点上的错误需要区分哨兵，而它们都没有对应。存储的错误仍对应不带参数的 `fail`：存储的 `fail` 只接受 timeout 和 refused，不能给出指定的 SQLSTATE 或驱动错误。

没有可注入对应物的效果：`branch` not_taken、`call` ok、`store_read` rows 的增加只说明执行次数变多；`check` 已有结果的增加同样可能只是执行变多；`rpc_*` 的 2xx/3xx 增加；`rpc_*` error 没有命名的动作；存储每次执行的行数增加是数据的变化，没有存储动作产生它。入口服务（gateway）`rpc_server` 的 4xx、5xx、error 是用户可见的终点。

## 4. 第一轮结果：业务代码

证据范围：一次实验，`runs/search/shop-stitching/`；shop 还没有上游组件（inventory 与 ledger 用 sqlite，orders 不缓存价格，即提交 `18f6989` 之前的 shop），只有业务代码中的 SDK 故障点；SDK 提交 `bb5168d`，服务和 `faultsearch` 使用的 faultpoint 分析代码都来自这一提交的 worktree；每个负载 3 次对照、3 次处理；8 个部署并行，全部运行约 55 分钟。只有一个随机种子。每次运行的原始数字、每条边和每条链都在该目录中，本节只给结论和支撑它的计数。

### 4.1 规模

- 目录：34 个故障点、90 个故障。2 个故障点只在服务启动时执行、不在任何租户的范围内（inventory 的 `main` 中的 `call`、orders 建表的 `store_write`），被排除。
- 预算：每种分配 240 次注入，是全部 540 个（故障，场景）对的 44%。分阶段分配中覆盖 90 次（65 次落在 baseline；25 次落在 strict-timeout，因为冷启动的超时重试使 inventory 和 orders 重试路径上的故障点在那里执行得更多），轮转 75 次，加权 75 次。
- 重复：场景对照 18 次；两种分配的处理合计 1038 次；哨兵发现越界、改为单独重跑的打包组 12 组 36 次；验证 15 次对照、33 次处理。

### 4.2 边与条件

分阶段分配得到 665 条边：301 条有条件（某个被测场景中不成立），364 条无条件，其中 97 条的原因故障只测过一个场景，无条件只是因为没有反例。413 条边的效果有目录中的对应故障，252 条没有。

| 边 | 成立 | 不成立 | 学到的条件 |
| --- | --- | --- | --- |
| orders 对 `/reserve` 的 `fail_after` timeout → inventory 缺货分支 taken | limited-stock | 其余 5 个场景 | `stock_per_sku=12` |
| inventory `handleReserve` 写入之后的 `err != nil` 处延迟 → orders 对 `/reserve` 超时 | strict-timeout | clearance-sale、tight-budget、limited-stock | `reserve_timeout_s=0.3` |
| gateway 对 orders、orders 对 `/charge` 的 `duplicate` → gateway 4xx | tight-budget | 其余被测场景 | `balance=3300`（重复扣款耗尽余额） |
| inventory 库存写入的 `duplicate`、`fail_after` → gateway 4xx | limited-stock | strict-timeout、baseline 等 | `stock_per_sku=12` |
| inventory 各处延迟 → gateway 2xx 均值增加 | 2 s 超时的各场景 | strict-timeout（请求被取消，不是变慢） | 析取，例如 `sku_numbers=[7,17,27]` 或 `balance=3300` 或 `stock_per_sku=12` |

第一行是已知的正例：每次重试都真的完成了预留，有限的库存被耗尽。分阶段分配和随机分配都找回了它，条件都是 `stock_per_sku=12`。

分阶段分配把故障分成 18 个因果等价的簇。簇大体按服务和动作的语义聚合，例如 inventory 写入之后的延迟、orders `retryable` 取反、orders 对 `/reserve` 的 `fail_after` timeout 是同一簇（都使 inventory 完成预留而 orders 仍然重试）；第一个场景中没有任何效果的故障（gateway 入口的注入、写入的 `drop`/`duplicate`、pricing 的 `discounted` 取反等）聚成一簇。

### 4.3 越过租户的影响

- **冷启动**：strict-timeout 的对照中，没有任何注入，每个租户的第一个请求也会超时失败（冷启动比 0.3 s 慢），对照的计数在重复间因此有波动。注入使被注入的租户先失败，后面的租户不再碰上冷启动，哨兵因此与对照不同；strict-timeout 中形成的打包组（1 组）因此改为单独运行，这个场景的 75 条处理记录都来自单独运行。这个冷启动来自挂上的 faultpoint：不挂 faultpoint 时，strict-timeout 的 84 次结账全部是 201；挂上而不带规则时，ledger 的第一次 `/charge` 在服务端用 210–236 ms（之后约 21 ms），orders 的 0.3 s 预算超时（`runs/shop/transparency-*`，SDK `eb49e50`）。其余 6 个场景挂与不挂的 84 个响应，状态码和正文逐条相同。
- **下一个请求**：orders 中未处理的异常（`price()` 和 `charge()` 不处理 httpx 的传输错误，价格或扣款超时就以异常结束；写入 orders 表失败同样如此）之后，紧接着的下一个请求在 gateway 的 fetch 处失败（outcome `error`，用户得到 502），不论它属于哪个租户。被哨兵发现越界的 12 个打包组中，11 个是这种情形（baseline、clearance-sale 各 3 组，bulk-orders、tight-budget 各 2 组，limited-stock 1 组），另 1 个是上面的冷启动。机制：Starlette 的 `ServerErrorMiddleware` 先发出一个不带 `Connection: close` 的 500，再把异常交给 uvicorn，uvicorn 随即关闭连接；gateway 的 fetch（undici）在收到 FIN 之前已经把排队的下一个请求写上这条连接，得到 “other side closed”，而 fetch 不重试 POST。不挂 SDK 时 20 次中 20 次复现；不经 Starlette 的 ASGI 应用和注册了异常处理的应用都不出现（`runs/python-sdk/keepalive_sample/`；`starlette/middleware/errors.py:149-186`，`uvicorn/protocols/http/h11_impl.py:409-420`）。
- **这是真实的效应，不是噪声**：范围只限制注入，不限制效应。服务之间共用的连接把一个租户的故障带给下一个请求，不论它属于哪个租户；以这样的失败为效果的边是真实的跨请求传播。搜索按被注入的租户比较效果，所以落在其他租户上的这类影响记录在处理记录的 `leakage` 中，不形成边。

### 4.4 链与验证

分阶段分配的边拼出 11627 条 4 跳以内的链：8868 条只靠拼接得到，2759 条单场景可见；另有 26 个环。验证排名前 10 的只靠拼接的链和前 3 的单场景可见的链：

| 链（首故障 → … → 终点） | 选取 | 合并负载 | 结果 |
| --- | --- | --- | --- |
| inventory 写入库存之后延迟 500 ms → orders 超时并重试 → 缺货分支 → orders 409 → 用户 4xx | 只靠拼接，第 6 | strict-timeout + limited-stock | 证实 |
| inventory 写入之后返回错误 → `retryable` 为真 → 缺货 → 用户 4xx（4 条，中间跳不同） | 只靠拼接，第 1、2、3、10 | strict-timeout + limited-stock | 证实 |
| inventory 缺货分支处（写入之前）延迟 500 ms → 超时 → … → 用户 4xx 或 5xx（5 条） | 只靠拼接，第 4、5、7、8、9 | strict-timeout（+ limited-stock 或 tight-budget） | 否定 |
| ledger 或 pricing 中延迟 500 ms → orders 的调用超时 → 用户 5xx（3 条） | 单场景可见 | strict-timeout | 证实 |

- **设想的链得到证实**：第一跳只在 strict-timeout 成立，第二跳只在 limited-stock 成立，没有一个被测场景显示全链。在合并负载中只注入链首的延迟，租户 a 的 21 次结账中 13 次缺货（409）、8 次 502，3 次重复完全相同；对照中全部是 201。inventory 写入完成后才变慢，orders 超时后重试，每次重试都再预留一次，库存被提前耗尽。
- **被否定的 5 条链都从写入之前的延迟出发**，否定的跳揭示了效果映射和条件的近似：
  - 超时的两个候选中实际成立的是 `fail` 而不是 `fail_after`：orders 超时断开后，Go 的请求上下文被取消，之后的数据库操作失败，预留没有发生（库存写入没有增加），缺货分支从未执行。
  - inventory 的错误（`handleReserve` 中 `err != nil` 为真）发生在 orders 已经超时离开之后，orders 看到的是超时，不是 5xx，“error → `fail` → 调用方 5xx”这一跳不成立。
  - “延迟使 `/reserve` 的 2xx 均值增加”只在超时为 2 s 的场景测到成立，学到的析取条件不含“超时仍是 2 s”，与 strict-timeout 合并后这一跳不成立。单参数的场景说明不了一条边在某个场景中不成立是因为哪个参数。
- 26 个环（例如 `retryable` 取反 → 库存写入增加 → `duplicate` → `/reserve` 均值增加 → 延迟 → `err != nil` 为真 → `fail` → `retryable` 为真）没有验证。

### 4.5 比较

**随机分配**（同样 240 次注入、同一种子）：

- 552 条边，其中 150 条有条件（分阶段分配为 665 和 301）。两者共有 483 条；只有分阶段分配找到的 182 条中 179 条有条件，只有随机分配找到的 69 条中 66 条有条件。分阶段分配在轮转和加权阶段把预算给了效果随场景变化的簇，多出来的几乎都是有条件的边。
- 只靠拼接、终止于用户可见失败的链：分阶段分配 784 条，随机 243 条；环 26 个对 0 个。
- 5 条证实的链，随机分配的边和链也都有：在 shop 这样的规模上，均匀抽取 44% 的（故障，场景）对已经覆盖了它们。5 条被否定的链，随机分配都没有（它没有在 strict-timeout 中注入缺货分支处的延迟）。

**单场景**：不拼接时，各场景的单次注入已经显示的（首故障，用户可见失败）对：baseline 36、strict-timeout 44、limited-stock 22、tight-budget 16、clearance-sale 15、bulk-orders 8，合计 69 个不同的对。分阶段分配只靠拼接、终止于用户可见失败的链覆盖 59 个这样的对，其中 33 个没有任何单次注入显示过。设想的链属于这 33 个：inventory 写入之后的延迟在 strict-timeout 中只让用户看到 5xx，在 limited-stock 等超时为 2 s 的场景中只使响应变慢，缺货的 4xx 只在合并负载中出现。

### 4.6 负面发现

- **值的变化没有观测点**：pricing 的 `discounted` 取反在 baseline、bulk-orders、strict-timeout 中测过，除了 strict-timeout 中冷启动的预热（第 4.3 节）没有任何效果：价格变了，但没有故障点观测价格。按代码中的价格计算，clearance-sale 的 SKU 全部打折，取反后每个租户的总价从 2883 升到 3627，超过 tight-budget 的余额 3300，ledger 会拒绝付款；这一组合没有运行。这条边不会出现，任何拼接都找不到经过它的链；要找到它，需要在价格计算上人工标注 `value` 故障点。
- **只能做终点的效果**：252 条边的效果没有可注入的对应故障，主要是执行次数的增加和 4xx 状态类别，它们只能结束一条链。
- **orders 的传输错误处理**：`price()` 和 `charge()` 不捕获 httpx 的传输错误，下游超时以未处理的异常（500）结束，而 `reserve()` 会重试；这是 shop 的业务代码本身的行为，并引出了第 4.3 节的越界。

## 5. 第二轮结果：业务代码、依赖库与上游组件

证据范围：一次实验，`runs/search/shop-layers/`；shop 带 Redis 价格缓存和 PostgreSQL 库存（提交 `18f6989` 起）；SDK 提交 `3b6a082`，服务和 `faultsearch` 使用的 faultpoint 都来自这一提交的 worktree；每个故障单独运行，每个负载 3 次对照、3 次处理；8 个部署并行，探索分三段运行，后两段沿用前面已完成的重复，连同验证共约 82 分钟（边和链从已有记录推导，三轮验证反馈新增的只有验证运行，约 7 分钟）。只做了分阶段分配，没有随机分配的对照。

### 5.1 规模

- 目录：182 个故障，业务层 136 个、依赖库层 37 个、上游层 9 个（PostgreSQL 的 `fdatasync` `pwrite64` `read` `recvfrom` `sendto` 与 Redis 的 `read` `write` 返回 EIO，两个容器发出的包延迟 500 ms）。依赖库中放置的点有 507 个从未在租户范围内执行，被“先观测、再注入”排除；库中的 5 个 `loop` 没有动作。
- 预算：360 次注入，是全部 1274 个（故障，场景）对的 28%：覆盖 182 次，轮转 89 次，加权 89 次。上游故障除覆盖外只再得到 1 次注入，多数只在一个场景中测过。
- 拒绝：ledger 的 Java agent 拒绝了它的 JDBC `store_write` 点上的 `duplicate` 和 `fail_after`（服务这类点的插件并非都实现这两个动作），这两个故障记为未执行，其余 357 次注入都实际执行了。

### 5.2 跨层的传播

上游故障单次注入就能显示跨越三层的传播：

| 上游故障 | 依赖库中的效果 | 业务层与用户 |
| --- | --- | --- |
| PostgreSQL 的 `read` `pwrite64` `fdatasync` `sendto` `recvfrom` 返回 EIO | pgxpool 的 `Acquire`、`QueryRow` 出错，puddle 建立资源（`initResourceValue`）出错，`fdatasync` 时连连接的建立都失败 | inventory 的错误分支，用户每次结账都得到 502 |

- **没有一条只靠拼接的跨层链被证实。**
- **证实的跨层链**：PostgreSQL 的 `recvfrom` 返回 EIO（作用于 postgres 容器）→ pgxpool `Acquire` 出错 →（pgxpool `QueryRow` 出错 →）orders 的 `retryable` 为真，或 orders 对 `/reserve` 的调用收到 5xx → 用户 5xx。层的序列是上游 > 依赖库 >（依赖库 >）业务 > 业务，每轮复核都是每一跳都出现。它们是单次注入就显示的传播，不需要拼接；依赖库中的结果不再对应故障之后，拼接不再产生这三条链，同一传播经由 inventory 的业务调用点出现。
- **只靠拼接的跨层链被否定的原因**：每一处拼接都把上一跳引起的结果换成在同一故障点上注入的同一结果；在 shop 中，只看结果说明不了接下来会发生什么。验证记录中的三种情形：
  - **重试之前有没有完成工作**：前两轮的 20 条链都经过“`retryable` 为真 → 把 `retryable` 取反”。取反让 orders 重试已经成功的预留，每次重试都再预留一次，在 limited-stock 中耗尽库存；而链首（上游的 EIO、在 pgxpool 内部注入的失败）使 inventory 在写入之前就失败，重试不消耗库存，缺货分支和库存写入的增加都没有出现。按三元组的反馈排除了被否定的后果（缺货分支），搜索随即找到同一个对应的另一个后果（库存写入增加），也被否定。这与第一轮“超时不说明对端是否已完成”是同一类问题。
  - **异常的类型**：在 redis-py 内部注入的失败抛出的异常越过了 orders 的 `create_order` 中的处理器（`create_order` 的调用出错），用户得到 502；拼接把这一结果对应到在这个调用点上注入 `fail`，而 SDK 在 Python 调用点上抛出处理器列出的第一个异常类，这里是 `OutOfStock`，用户得到 409。
  - **错误是否在调用方的超时之前到达**：PostgreSQL 的包延迟下，inventory 在 3 次处理中每次都返回 15 次 5xx，orders 对 `/reserve` 的调用每次也都有 15 次超时：错误在 orders 超时之后才到达，orders 不读状态码就重试，`retryable` 不会因此为真；拼接把 inventory 的错误对应到在它的调用点上注入 `fail`，后者立刻返回 5xx。
  - 这三种区别（工作是否已完成、异常的类型、错误相对于超时的时机）都不在观测的 outcome 中，效果映射也就无从区分。
- 已知的正例（`/reserve` 的 `fail_after` 超时耗尽有限的库存）在第二轮的分配中没有被注入到 limited-stock，这一边没有出现；改用 PostgreSQL 之后它仍然成立：用 SDK `3b6a082` 和提交 `18f6989` 的 shop，`examples/shop/experiment.py` 在 limited-stock 中运行 2 次对照、2 次处理，租户 a 的缺货分支每次 37 次（`runs/shop/experiment-3b6a082.out`）。

### 6.3 检验：不经过已完成工作的对应

证据范围：实验 `runs/search/shop-boundary-counterparts/`，与第 6.1 节同一构建（`a4bc35e`，shop 从它重建），沿用那里的全部记录，现在的效果映射（第 3.3 节）记为它的输入。

- **假设**：第 6.2 节的否定都来自改变了自然原因没有碰到的执行的对应：`check` 的取反、`branch` 的 `fail`、Go 调用点在被调用者执行之后的 `fail`。把这三类效果改为没有对应，拼接就只能经过它们背后的原因的边界效果，例如阳性对照中“orders 对 `/reserve` 的调用收到 500 → 在这个客户端注入 `fail status=500`”。
- **预言**：经过这三类对应的只靠拼接的链消失；剩下的链若被否定，原因不是工作是否已经完成。
- **代价**：新映射只去掉对应，不需要新的对应故障，0 次注入。Go 调用点的错误都没有对应，按清单区分已登记哨兵的规则用不上，所以 `a4bc35e` 的清单没有 `errors` 不影响结果。

  | 选取 | 条数 | 证实 | 否定 |
  | --- | --- | --- | --- |
  | 跨层、只靠拼接、终止于用户 | 5 | 0 | 5 |
  | 阳性对照 | 3 | 3 | 0 |

  - 包延迟起头的 3 条（上游 > 业务 > 业务 > 业务）在第 2 跳断开：期待 orders 对 `/reserve` 的调用收到 5xx `status=500`，实际是 timeout `error=httpx.ReadTimeout sent=true`，每次 15 次。inventory 的 500 在 orders 离开之后才答复（其中一条的第一跳就是 inventory 服务端的 5xx `abandoned=true status=500`），拼接却把它对应到立即答复的 `fail status=500`，或 inventory 存储上的 `fail`。
  - pgxpool、puddle 起头的 2 条（依赖库 > 上游 > 业务 > 业务）在第 2 跳断开：期待 inventory 的 `stock` 读取以 `*pgconn.ConnectError` 失败，实际以 `*fppoints.injectedError` 失败，每次 3 次，这是链首自己注入的错误。`pq_getbyte` 读到的 EOF 是 inventory 关闭连接的结果，不是原因，拼接把方向反了过来。
- **结论**：两个预言都成立。之前的 1288 条链都经过这三类对应，去掉之后，shop 中几乎不剩只靠拼接的跨层链，忠实的对应拼出的链在单个场景中已经可见。剩下的 5 条被否定，原因是时机（服务端在调用方离开后才答复）和方向（上游的自然结果是业务服务行为的结果）。细节记下了前者（`abandoned=true`），这一次的效果映射对服务端的状态还没有用它；后者是效果的因果方向，观测不记录。

第二次检验：实验 `runs/search/shop-faithful-counterparts/`，同一构建，沿用上一次检验的全部记录。

- **假设**：剩下的两种否定是同一类：记下“对端已经离开”的观测是对端的结果，不是这一处的原因。inventory 的 5xx `abandoned=true` 是 inventory 注意到 orders 已离开；`pq_getbyte` 自然的 EOF 是 PostgreSQL 注意到 inventory 关闭了连接。忠实的对应在对端（orders 的超时、inventory 自己的失败），链本来就能到达。规则：服务端 `abandoned=true` 的效果没有对应；原生函数中表示客户端离开的结果没有对应，目前是 `pq_getbyte` 的 EOF，作为数据写在效果映射的按函数规则中。
- **预言**：经过这两类对应的链消失；剩下的若被否定，原因不是对端已离开。
- **代价**：0 次新的注入；验证全部沿用已有的记录，0 次新的重复。
- **结果**：3781 条边、133437 条链。跨层、只靠拼接、终止于用户的链剩 4 条，全部在基线中、以 PostgreSQL 的包延迟起头、终止于 `/checkout` 502：包延迟 → inventory 的 `stock` 读或写以 `*errors.errorString` 失败 → 在这个存储点注入 `fail` → orders 对 `/reserve` 的调用收到 500，或 inventory 服务端答复 500 → 用户 502。它们只有一种（层，终点），按每对最多 3 条验证 3 条，另验证与上一次相同的 3 条阳性对照：

  | 选取 | 条数 | 证实 | 否定 |
  | --- | --- | --- | --- |
  | 跨层、只靠拼接、终止于用户 | 3 | 0 | 3 |
  | 阳性对照 | 3 | 3 | 0 |

  3 条都在第 2 跳断开：期待 orders 收到 500，实际是 timeout `sent=true`，每次 15 次（2 条）；期待 inventory 服务端答复 5xx `abandoned=false status=500`，实际是 5xx `abandoned=true status=500`，每次 15 次（1 条）。
- **结论**：第一个预言成立；第二个不成立：剩下的否定仍是对端已离开。包延迟使 orders 先超时离开，inventory 的存储调用随后才失败，`*errors.errorString` 也是 Go 的 `context.Canceled` 的类型；存储点的细节没有 `abandoned`，观测不说明这个失败发生在调用方离开之后，效果映射就把它当作原因。

## 7. 局限

- **总的发现**：在 shop 中，对应故障忠实之后，跨层的链只经由 inventory 和 PostgreSQL 到达用户，而这些链在单个场景中已经可见。只靠拼接得到的跨层链，都经过不忠实的对应：取反、分支和 Go 调用点上改变了自然原因没有碰到的执行的注入，或把对端已离开的结果当作原因。

- 一次实验、一个随机种子；随机分配与分阶段分配的比较只针对第一轮的这一次抽样。
- 计数的下限是固定的 20%：上游后台工作随运行时长的增加大多在 5% 以内，被它去掉；低于 20% 的真实增加（例如 33 次 Redis 命令多出 3 次）也被去掉。按运行时长归一化范围之外的计数，可以不靠这个下限。
- 效果映射不知道调用方看到失败时工作是否已经完成，所以 `check`、`branch`、Go 调用点和依赖库中的结果都不对应故障，拼接只经过边界效果（第 6.3 节）。
- 拼接不知道效果的因果方向：服务端的 `abandoned` 和 `pq_getbyte` 的 EOF 标出了“对端已经离开”，其他点上同样由对端离开引起的失败（例如 inventory 在 orders 离开之后的存储错误）没有这样的细节，仍被当作原因（第 6.3 节）。
- 注入的错误以 SDK 自己的类型出现在下游的细节中（`faultpoint/internal/action.ErrInjected`、`*fppoints.injectedError`），与自然错误的类型不同，经过这类效果的拼接在键上就与自然的传播不一致。
- 验证反馈按（效果，对应的故障，后果）三元组排除被否定的步，同一个不忠实的对应可以经由下一个后果再次出现；反馈只能逐步收敛，不能推广到同一类对应。
- 依赖库中的热路径故障点没有延迟动作；库中的 `fail` 可能使连接池进入真实系统不会进入的状态，结论限于它实际表现出的行为。
- 一次重复最多发送 120 s 的结账，使整个服务停住的故障只观测到前 120 s。
- 条件只从单参数场景学习：分不清一条边在某个场景中不成立是因为哪个参数，析取条件合并时可能丢掉必要的基线值（第 4.4 节被否定的第三类链）。原因故障只测过一个场景的边，条件只是把那个场景与基线区分开。
- 效果到故障的映射是近似：均值增加一律对应 500 ms 的延迟，幅度没有学习，目录中的延迟只有 500 ms 一种幅度；请求已发出、却没有服务端在调用方离开后答复的超时没有对应。
- 原生函数点只有两个，`pq_getbyte` 的 EOF 与 `recvfrom` 的 EIO 效果相近；存储的错误不能按 SQLSTATE 或驱动错误注入。
- 打包只能发现越过到哨兵租户的影响；哨兵与被注入租户交替排列，覆盖“影响下一个请求”和“影响之后所有请求”两种情形，其他形状的越界会漏掉。
- 越过租户的影响不形成边；环没有验证。
- 束搜索在 shop 的图上等于穷举；更大的系统需要有限的束宽，排序和剪枝的取舍还没有在那种规模上检验。
- 排名前 10 的只靠拼接的链有一半被否定，被否定的都经过“写入之前的延迟 → 超时”这一跳；排序没有利用这种按效果映射近似程度区分可信度的信息。

## 8. 机制验证：构造的系统上的跨层拼接

这一节是在专门构造的系统上验证机制，不是对真实系统的发现，不能当作 shop 或其他系统中存在这类链路的证据。第 5 至 7 节的结论来自 shop：在 shop 中，替代故障忠实之后，跨层链路在单个场景中已经可见。这里单独回答一个机制问题：如果一条跨层链路只在两个场景合起来时才出现，在替代故障忠实的前提下，拼接能不能找到它，合并负载的验证能不能确认它。

本节在构建和运行之前写成并提交，预先登记系统、两条链路和预期结果；之后的结果另起一小节写，这一小节不按结果修改。构造检查（第 8.3 节）若要求改动构造参数，改动记在结果中，不改这里的登记。

### 8.1 系统：`examples/stitch-mechanism`

两个业务服务、两种语言，两个上游组件：

- **quote（Python，Starlette 与 httpx）**：用户入口 `POST /quotes`，请求带租户、SKU 和 `guaranteed`。它向 catalog 查价，超时 2 s。catalog 答复 5xx 或连接失败时：`guaranteed` 为真，答复用户 503；否则按自己的标价表报价，答复 200，并标明是估价。业务理由：普通询价可以先给估价，承诺价格的询价（例如企业客户）只能给实时价格。
- **catalog（Go，net/http、go-redis、pgx）**：`GET /prices/{sku}`。先读 Redis 中的价格；未命中时从 PostgreSQL 计算价格，再写回 Redis（600 s）。计算要扫描折扣规则表，没有索引，目标约 40 ms。连接池最多 2 个连接，每个请求的数据库预算 100 ms（context 截止时间）。错误是 `context.DeadlineExceeded` 时答复 503（忙），其他错误答复 500。业务理由：缓存挡住大部分询价，数据库只为少数未缓存的商品计算价格。
- **上游组件**：Redis（价格缓存）和 PostgreSQL（价格与折扣规则），每次重复都是新的容器，内核代理在两个容器上放系统调用、包和原生函数点（Redis 的 `lookupKey`、PostgreSQL 的 `pq_getbyte`，与 shop 相同）。
- **数据**：4 个租户，每个租户 3 个 SKU，每个租户发 21 次询价，依次轮换 SKU。种子把每个租户的前两个 SKU 写进 Redis，第三个 SKU 是新商品，没有缓存，所以每次重复中每个租户自然地有一次未命中，catalog 的数据库路径在对照中执行过。

场景，每个只改基线的一个参数：

| 场景 | 改动 | 业务理由 |
| --- | --- | --- |
| `baseline` | 并发 1，`guaranteed` 为假 | 平常的询价，顺序到达，接受估价 |
| `flash-sale` | 并发 8 | 限时促销，许多客户同时询价 |
| `price-guarantee` | `guaranteed` 为真 | 企业客户只接受实时价格 |

### 8.2 预先登记的链路

**正面链路 P**，预期能找到并被确认：

1. 起点：Redis 的 `lookupKey` 注入 `fail error=NULL`（上游层，原生函数，作用于整个 Redis 容器）。每次读缓存都未命中。
2. 第一跳：catalog 的 `GET /prices/{}` 答复 5xx `status=503`。只在 flash-sale 成立：8 个并发的未命中争用 2 个连接，等待超过 100 ms。基线和 price-guarantee 中未命中是顺序的，每次约 40 ms，不超时。
3. 第二跳：在 catalog 的服务端注入 `fail status=503`，用户在 quote 的 `POST /quotes` 得到 5xx `status=503`。只在 price-guarantee 成立：其他场景中 quote 给估价，用户得到 200。
4. 预期：没有一个被测场景显示全部跳：flash-sale 中用户得到估价，price-guarantee 中未命中不会耗尽连接池。所以 P 只靠拼接得到。拼接应当找到它，或找到同一起点、同一终点、经过 quote 客户端收到的 503（`fail status=503` 在 quote 的客户端）的同类链路。在合并负载 `{并发 8, guaranteed 为真}` 中只注入起点，每一跳都应出现。

**反面对照 N**，预期能拼出来但被否定：

1. 起点同 P。
2. 第一跳：catalog 读价格的存储点出错，错误是截止时间（flash-sale）；或 catalog 中调用计算价格的 Go 调用点出错（若这个调用是放置在调用处的点）。
3. 第二跳：在这个存储点或调用点注入 `fail`，catalog 答复 5xx `status=500`。在命中未缓存 SKU 的请求中，每个场景都成立。
4. 第三跳：在 catalog 的服务端注入 `fail status=500`，用户得到 503（price-guarantee）。
5. 为什么不忠实：自然的错误是 `context.DeadlineExceeded`，catalog 把它答成 503。注入的存储 `fail` 或 Go 调用 `fail` 带的是 SDK 的错误，不是 `context.DeadlineExceeded`（它是标准库的哨兵，不在构建登记的错误中），catalog 把它答成 500。
6. 预期：拼接能拼出 N。在与 P 相同的合并负载中验证时，预期在“catalog 答复 `status=500`”那一跳被否定：实际是 503。

### 8.3 构造检查

搜索之前，用单个注入确认构造是对的。这是构造的真值，不是搜索的结果：

1. `lookupKey` 注入 NULL：flash-sale 中 catalog 出现 503，而用户都是 200；基线和 price-guarantee 中 catalog 没有 503。
2. catalog 服务端注入 `fail status=503`（租户 a）：price-guarantee 中租户 a 的用户得到 503；基线和 flash-sale 中用户都是 200。
3. `lookupKey` 注入 NULL，在合并负载 `{并发 8, guaranteed 为真}` 中：用户得到 503。

三条不全成立时，只改构造参数（规则表的行数、数据库预算、连接池大小），再检查一遍，改动记在结果中；搜索的设置和效果映射不因此改动。

### 8.4 搜索设置与判定

- **构建**：当时的 HEAD。效果映射中 Go 调用点的对应按 945ca8c 以后的语义恢复：构建登记的哨兵对应 `fail error=<名字>`，其他错误对应不带错误的 `fail`，因为 `fail` 跳过被调函数。
- **流程**：先观测再注入、编目、分阶段分配（预算等于全部（故障，场景）对，分配不成为瓶颈）、拼接、补跑对应故障、再拼接、合并负载验证。每个负载 3 次对照、3 次处理，计数下限 0.2，均值下限 0.5。
- **验证的链**：
  - 跨层、只靠拼接、终止于用户可见失败的链中排名最前的最多 10 条，每种（第一个故障的层，最后的效果）最多 3 条；
  - P 和 N 两类中排名最前的各一条，按键指定；
  - 至多 3 条单场景可见的跨层链作为阳性对照。
- **判定**：
  - P 是否被找到，在全部链中和在只靠拼接的跨层链中各排第几，验证是否确认；
  - N 是否被否定，在哪一跳；
  - 前 10 条只靠拼接的跨层链中确认的条数，以及其余各条被否定的跳和原因。
- **解读**：P 被确认、N 被否定，只说明在一个构造的情形中，这一机制能找到并确认跨场景的跨层链路，并能否定不忠实的对应；不说明真实系统中存在这样的链路。

### 8.5 补登：变体 N′ 与租户之间的越界

这一小节在第 8.1 至 8.4 节之后、任何搜索运行之前补登。构造检查已经跑过，它的结果和构造参数的改动写在结果中。

**变体 N′**：catalog 的构建写 `placement.error_packages: ["context"]`，其余与原设置相同。`context.DeadlineExceeded` 和 `context.Canceled` 因此由 catalog 的每个改写过的包登记，并写进清单的 errors。观测给错误命名时按 `errors.Is` 先找登记过的错误，所以截止时间的错误，不论是 pgx 包装过的，还是等连接时直接返回的，都记成 `context.DeadlineExceeded`。两种构建算两次实验，各自一个构建目录，各自走完整个流程，结果分开报告。

预测，按 SDK 代码和效果映射推出：

1. 原设置下，N 按第 8.2 节被否定。调用点那一跳对应不带错误的 `fail`，返回 SDK 自己的错误；存储点那一跳对应不带错误的 `fail`，返回 SDK 的 `ErrInjected`。两者都不是 `context.DeadlineExceeded`，catalog 答 500。
2. N′ 经过调用点（catalog 中调用计算价格的调用点，或 `handlePrice` 中调用 `price` 的调用点）：自然错误是登记过的哨兵，对应是 `fail error=context.DeadlineExceeded`。`fail` 跳过被调函数，返回这个哨兵，catalog 答 503。这一跳因此是忠实的。拼出的链在这一跳之后是 catalog 答 503，再到用户 503，与 P 同起点、同终点，预期在合并负载中被确认。
3. N′ 经过存储点（计算价格的那条语句）：效果映射中存储错误的规则对应不带错误的 `fail`，不看错误名；Go 的存储 `fail` 只有写了 `error=timeout` 才返回 `context.DeadlineExceeded`。所以这一跳在 N′ 中仍不忠实，链仍到 catalog 答 500，预期仍被否定。

判定增加两项：N′ 经过调用点的链是否找到、是否被确认；N′ 经过存储点的链是否仍被否定。

**租户之间的越界**：shop 的透明检查中，一个请求里未处理的异常使服务关闭了与调用方共用的 keep-alive 连接，下一个租户的请求复用这条连接而失败。本系统中各处的情形：

- 用户到 quote：每个请求一个新连接（urllib 发 `Connection: close`），quote 里未处理的异常只影响这一个请求。
- quote 到 catalog：httpx 的连接池复用连接。catalog 对每个错误都答一个状态码，不 panic；只有 `crash` 结束整个进程，这是那个故障本身的效果。
- catalog 的数据库连接和 Redis 为全部租户共用。这是构造的机制，flash-sale 中租户争用同一个连接；但一个作用于租户 a 的延迟或重复类故障也会占住这个连接，使其他租户的请求超时。

处理：不按租户分开部署，否则 flash-sale 的争用不复存在。搜索把故障放在各自的重复中，效果按被注入的租户的记录和不属于任何租户的记录比较。其他租户的服务记录不进入边，但上游组件的记录汇总全部租户，越界可以经过它们进入边。所以每次验证的第一个故障若作用于一个租户，结果中同时报告其他租户的用户状态相对对照的差别，作为越界的度量。

### 8.6 结果

证据范围：两次实验，`runs/search/stitch-mechanism-plain/`（catalog 不登记 context 的错误）和 `runs/search/stitch-mechanism-context-sentinels/`（变体 N′）。两者都用 SDK `e182ac3` 的 worktree（含 go-sdk 的 `d350768`，带 JOIN 的 SELECT 归为读，计算价格的语句因此是 `catalog:store_read:discount_rules+prices#06d18153`），系统代码来自 `6c497a5`，各自一个构建目录。每个故障单独运行，每个负载 3 次对照、3 次处理，6 个部署并行。按每次重复的文件时间：普通构建 09:39–09:57，423 次重复；变体 09:57–10:15，447 次重复；验证在 10:39–10:40，分别 24 次和 18 次重复。主机 24 核；探索期间 1 分钟负载均值 14.9（10.6–20.4）和 14.5（9.7–25.1），验证期间 7.6–14.6，每 30 秒的记录在 `runs/search/stitch-mechanism-loadavg.log`，从 09:39:42 开始，漏掉普通构建最初的 24 秒。只有一个随机种子。

  - 第 2 项：catalog 服务端注入 `fail status=503` 后，只有 price-guarantee 中用户得到 503，21/21。
  - 第 3 项：合并负载中，用户 503 在普通构建为 14/16/17，在变体为 12/16/17。
- 两个构建只差错误的命名。截止时间的错误在普通构建中记成 `*pgconn.errTimeout`（查询中途到期）或 `context.deadlineExceededError`（等连接时到期），在变体中都记成 `context.DeadlineExceeded`。两者清单的 errors 分别是空和 `context.Canceled`、`context.DeadlineExceeded`。

#### 本底噪声

合并负载 `{并发 24, guaranteed 为真}` 的对照本身就有 503：未缓存 SKU 的第一波请求同时未命中，排在同一个连接后面。

- 每次重复中全部租户的用户 503：
  - 三次通过的构造检查（改参数后的第二次、普通构建、变体），对照分别是 5/6/0、0/6/0、0/0/1；
  - 验证的对照中，catalog 的 5xx 普通构建是 5/0/0，变体是 2/3/2；
  - 租户 a 的用户 503，普通构建 0/0/0，变体 0/2/0。
- 本底的用户 503 只出现在合并负载里。flash-sale 的探索对照中，catalog 的 5xx 普通构建为 2/0/2、变体为 0/0/0，但那里的用户得到估价，全部是 200。
- 下面的判定都按同一合并负载中对照与处理的差。
- 这些对照运行时的 1 分钟负载在 7.6 到 15.4 之间。点太少，看不出负载与超时的关系；只有第一次构造检查在负载 95 时，并发 1 也超时。

- **中间效果的错误名来自对应注入：** `ErrInjected`、`*fppoints.injectedError`、`*errors.errorString`，自然的是 `ConnectError`、`errTimeout` 或 `Canceled`。效果键带着错误名，所以这一跳在自然的运行中不会出现。

#### 单场景可见的跨层对照

- **普通构建：** 3 条全部确认。两条从 PostgreSQL 发出的包延迟 500 ms 开始，一条从 `pq_getbyte` EOF 开始，都经语句出错、缓存未命中到用户 503。未命中由 4/3/4 增到 7/7/7，其余各跳都由 0 增到 7/7/7。
- **变体：** 3 条全部否定，否定都在未命中那一跳：
  - 两条要求 `GET price:{}` 未命中增加。合并负载的对照中租户 a 的未命中是 3/7/5，处理是 7/7/7。7 是上限（每个租户有 7 次询价落在未缓存的 SKU 上），对照的波动使检验不显著。
  - 另一条要求 Redis `lookupKey` 未命中增加，对照为 25/26/25，处理为 28/25/26。
  - 其余各跳都确认了：PriceUnavailable 和用户 503 由 0/2/0 增到 7/7/7。
- 这是合并负载本底噪声的直接后果：同一组链，在对照较安静的普通构建中被确认。

#### 越过租户的影响

验证中第一个故障作用于租户 a 的链，其他三个租户的用户 503 合计（每次重复）：

- **普通构建，`SET price:{}` `drop`：** 对照 5/0/0，处理 3/5/5。处理记录的 `leakage` 中，租户 b 的缓存命中由 14 增到 18，租户 c 的计算价格调用由 4/4/3 增到 5/5/5。
- **变体，语句 `empty`：** 对照 2/1/2，处理 4/2/3，`leakage` 为空。

普通构建的增加与经共用的数据库连接越界相符，但对照本底（5/0/0）与它同一量级，这里不据此认定越界。

#### 已知问题

- quote 也是 Starlette 和 uvicorn，但第 4.3 节那种“下一个请求”的失败不在这条路径上：用户到 quote 每个请求一个新连接，quote 到 catalog 是 httpx 连到 Go 的 net/http。
- python-sdk 发现 uvicorn 停止时会丢掉最后不到 2 秒的观测，正在修。这里的部署在负载结束后等三个写出间隔（1.5 s）才停止服务；两次实验的 912 次重复中，quote 服务端记录的请求数与用户收到的响应数全部相同。

#### 解读

- **机制能做到的：** 在这个构造的情形中，只在两个场景合起来时才出现的跨层链路 P 被拼接找到，并在合并负载中被确认，两种构建都如此。不忠实的对应 N 被否定在预测的那一跳；登记标准库哨兵之后，调用点的对应变得忠实，N′ 经调用点被确认，经存储点仍被否定。
- **排名没有把 P 排在前面：** 预先登记的前 10 条，每次实验实际选出 6 条，两次实验共确认 1 条，而这 1 条其实是单场景可见的链。排名在前的链，多数带着由对应注入的错误名决定的中间效果，或带着在合并负载中测不出的计数效果。
- **因此：** 只靠排名选链验证，这次找不到 P；P 是按键指定后才被验证的。
- **范围：** 这些结论不说明真实系统中存在这样的链路。
